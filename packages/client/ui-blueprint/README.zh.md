# @deepseek-ai/dsh-client-ui-blueprint

[English](README.md) | 中文

现有 DSH Web 外壳中的第一版可用 Interactive Blueprint Agent Builder。它填充四个已声明 slot：侧栏中的 Agent 名单、详情栏中的 Blueprint、composer 上方的 selected context，以及 frame overlay 中的试用确认对话框。

当前 Session 及 Host 回显的 `agentPreset` 持有默认 Blueprint target。浏览器 preference 会把 override 与该 Session id 一起保存，因此显式选择 Agent 只会改变一个 Session 的右侧 target，不会泄露到其他 Session 或空白新会话页面。Creator record 或绑定 target 的 capability-authoring record 只有属于同一 Session 时才能覆盖 runtime preset。每次 current Session 变化时，controller 都会先清除上一份投影，再读取新的 runtime identity，并按 `同 Session authoring target → 同 Session 显式选择 → runtime agentPreset → 部署默认项` 重新投影；不存在或不可读的项目会被丢弃。在 Agent 名单中选择 Creator 只会为下一个 Session 暂存 `cordis`，不会给当前 Session 换标签。该 Creator Session 收到创建请求前，基础 `cordis` 投影仍可显示在 UI 中，但不会安装为普通 existing-Agent 模型上下文；首个 Creator prompt 因此不会继承 Proposal 或新 Agent 路由指令。详情栏会把投影节点分组到 Identity、Purpose、Capabilities、Behavior 与 Output，但不翻译 semantic value。固定 label 只对 `zh` source-language tag 使用中文，其余语言暂时 fallback 英文；label fallback 绝不会改变 Agent 的已编写语言。其他直接编辑按钮与 capability 开关遵循 `editable: true`。Purpose 会完整显示 committed text，并复用包含「取消」与「提交修改」的原有行内文本编辑器；只读 legacy Identity 则显示「调整」，但不会声称 Host 存在安全写入。

Creator 恢复与异步投影只向当前 Session 的当前前台代次发布。切走不会删除 authoring 历史或停止后台执行；返回或刷新会恢复该 Session 自己的 lifecycle。来源可以在 handoff 前展示自己的暂存 Draft，但不能接管子 Creator 的状态。Foreign 或已过期结果不能改变 target、context 或交互锁。参见[前台归属决策](../../../.agents/notes/implemented/bug-fix/2026-08-28-blueprint-creator-foreground-ownership.md)。

所有可编辑的 Identity、Purpose、Behavior、Output、Web Search 与 Web Fetch 控件都使用同一条结构化 interaction 路径。「提交」会创建 client route id，并通过 conversation-context 同步发送 source Session、所选 node 及其类型、committed expected value 与 proposed scalar；它不会调用单 node 写入 Remote，也不会更新 Blueprint store。Host 会对照新的 committed projection 校验该编辑，推导其 operation 与确定性的 P2 candidate，记录并刷新 route-owned input，唤醒 source conversation，并在不写 preset 的前提下返回匹配的 enqueue evidence。Client 会拒绝缺失或属于其他 interaction 的 evidence；editor 提交失败后会保持打开并保留 draft。生成的 Proposal 卡片会接受每种受支持的结构化 node 类型，在通用文案中保留 source label，并拒绝 Access。因此，只有应用生成的 Change Set 后，committed Blueprint 才会变化。Apply 会根据 source Session 中持久化的 Proposal Tool 成功结果重新授权确切操作，记录 route-owned receipt，并执行一次最终重新投影。UI 不会把 draft、Proposal value 或模型文案当作 committed Agent state。选中 node 会把可选上下文同步到当前对话，但绝不会修改 preset。

控制器使用与 provider 无关的 Agent catalog 和 Blueprint operation interface。DSH Web binding 会把真实 preset 名单与 Host Remote 映射到这套接口。`InMemoryBlueprintDemoAdapter` 通过调用方提供的 seed data 实现同一套名单、投影、窄写入、能力开关、原子 Apply 与重置行为，使静态高保真 Demo 可以复用控制器，而不必内置最终示例名单或模拟完整 DSH API。它不会创建 Session、调用模型、编写 Skill 或报告 runtime conformance。

Demo Mode 是另一种 data binding，不是另一张页面。`mountBlueprintDemoUi` 会把 production roster、details panel、selected-context chip、proposal row 与 trial overlay 注册到正常 DSH slot 中。可选的 Host composition 可以提供 `demoBootstrapJson`；Host 半会在 shell 启动前注入解析后的文档，built Web shell 仅在同时存在 `?fixture&blueprintDemo` 时启用该 binding。layout、theme、navigation、conversation 与 component CSS 仍完全使用真实 Web Client 实现。可选的 `creatorScenario` 在使用真实 `cordis` preset 的 Fixture Session 收到明确的新建 Agent 请求前不会进入名单。Fixture event 随后驱动 Creator 进度与原生授权，Demo-local coordination 则发布 Purpose 修改、Skill node、协作 Agent node 与试用验证。该流程不会调用模型、Tool 实现、Agent loop、Host 写入或网络 endpoint。验证状态只记录确定性 Demo flag，不得表述为 runtime conformance。仓库通过可运行的 `examples/web-blueprint-demo` overlay 提供预览入口。

`DemoScenarioController` 统一持有 walkthrough lifecycle、Creator projection、Blueprint selection、proposal、capability authoring 与 trial state，只向现有 component 投影兼容字段。connection fixture 通过单一 timeline player，使用 production `SessionEvent` 与 pending-interaction frame 字段构造 transcript。这些可替换 fixture input 用于后续产品与原型对比，不定义最终 interaction behavior。

「能力」只有一个克制的 `＋ 添加能力` 入口，并从真实 Purpose、Behavior、Output 节点与已挂载 runtime evidence 派生最多六条可重复执行的具体工作。投递跟踪、供应商尽调、估值比较或访谈主题聚类等 Agent 特有工作必须有 semantic source evidence。已启用 Web Search 与 File Read 也会得到简洁的用户级条目，因为漏掉真实主要能力会误导用户；这些条目只有在对应 Tool node 确实 active 时才存在。限定于 preset 的 Skill 与 provider-backed delegation 保留自己的 evidence，而 inherited catalog 不会展开为组件清单。每条陈述会在内部保留其语义与 runtime supporting node id；UI 只按 Blueprint source language 或既有英文 label fallback 显示简洁工作名称。选择一条陈述会把一个真实 supporting node 作为对话 context。

「添加能力」会询问当前 Agent 还应做什么，并使用新的 `routeId` 启动绑定 target 的配置状态。普通对话会收到用户原始目标，并且必须先判断当前 editable Blueprint 是否足以实现；这条路径继续开放 `propose_blueprint_change`，但 Identity、Purpose 与 Behavior 文本不能近似实现添加能力请求。只有携带同一 route 与 source Session 的类型化 `route_blueprint_capability_authoring` 结果，才能把确实需要新 Skill 定义或 Subagent 配置的需求转入 Creator authoring。该路由保留当前 preset id 与 revision，绝不会创建或复制第二个顶层 preset。当 source 已运行 `cordis` 时，该 Session 会在 routing turn 结束后直接持有 authoring 与 repair；Client 不分配 capability worker，内部 lifecycle transcript 会持久化但不进入普通对话。非 `cordis` source 仍保留 deterministic dedicated-worker fallback，旧的后台记录也继续可恢复。Source Session 与 route 同时持有 UI 状态和执行。该 lifecycle 处于 active 状态时，edit、Apply、再次 Add 与 Try 均不可用。持久 baseline 会保留 target revision、preset roster、projected node、Skill 与 delegation；成功 terminal 只允许所选 capability delta，并拒绝无关 semantic change 或额外 preset。Controller 按 source Session 保留最近一次 interaction，只为当前 foreground 派生可见 handoff，后台扫描仅处理 legacy distinct worker。Pending observation 会匹配确切 route，而不再只匹配 target 与 revision。刷新恢复会重建 lifecycle 的 source、route 与 terminal outcome，不使用本地 completion 存储；同一 source 的新能力请求会替换此前 terminal。取消同源 authoring 只结束该 lifecycle 及其确切 inbox input；legacy dedicated worker 仍可整体停止。失败的 prompt continuation 使用同一 quiescence fence，因此丢失响应不能在 authoring 仍可写入时发布 failure。Skill 与 Subagent 都必须通过 fresh target-bound runtime verification 才能发布；只描述规格的回复会失败。

明确的修改请求可以在对话中生成类型化 Change Proposal。它的 Change Set 携带 source Session 与 interaction route。Session scoped row 只在 Change Set id 与该 Tool row 的确切 call id 相同时接纳 metadata；对于 structured edit，第一项 proposal 还必须匹配 source node id 与 type、对应 operation、该 operation 的 scalar type，并且 current value 与 proposed value 确实不同。该 row 只为这个 owner 渲染；前台导航以及同一 target 上的另一 interaction 都不能迁移卡片。卡片只显示修改效果与影响说明；用户点击 Apply 前不会调用任何写方法。Apply 会把确切 owner 与闭集操作发送到 `blueprint.applyChangeSet`；Host 会定位 source Session 中成功的 Proposal Tool result，重建其中的 operation，并在任何 preset 写入前拒绝缺失、属于其他 owner 或被修改的请求。Apply 与 Cancel 共用一个按 preset 串行执行的 terminal decision。重复同一 decision 是幂等操作，相反 decision 会被拒绝；两种 outcome 都会在返回前刷新到 source Session。成功事务会在一次原子 preset 发布中提交全部已通过 preflight 的 operation，或者一项也不提交；随后 client 只执行一次最终 `blueprint.get`。带保护的恢复或并发更改结果也会刷新，而 preflight 与 staging 失败会保持当前 Blueprint 不变。讨论、判断与假设性消息不会生成卡片。

在 `cordis` Creator Session 中，用户明确提出创建、搭建或想要一个有名称的 Agent 时会启动一份 Session scoped Draft。后续子句暂缓不相关的 Skill 或 Subagent authoring 时，不会否定前面的主要创建请求；局部受到否定的创建 Agent 表达则不会启动 Draft。协调器会立即清除旧 Blueprint 与可编辑的对话 target，并从现有 running 状态、终止 turn 原因以及原生 question 或 approval interaction 推导 Creating、Waiting 和 Paused。页面重新挂载后，它可以从 Session 中的持久 user message、已结束 Tool result、待处理 interaction 与最近 turn end 重建 lifecycle；创建前名单通过排除随后 authoring 证据归属的 preset 来恢复，不会把刷新时的当前名单直接当作 baseline。Creating、Waiting、Paused 与 Ambiguity 会安装 Creator authoring context 并移除 Proposal Tool，因此原生问卷的结构化回答会继续 authoring，不会被重新解释为修改 existing Agent。已结束的 `preset_copy` 会直接贡献其类型化 source 与 target id。明确的原生问卷选择会区分使用已有 preset、基于已有 preset 完善与新建独立 preset。选择使用已有 preset 时可以立即接纳指定 baseline preset；策略尚未决定时，只有当前 Session 已对某个 metadata 名称与 Draft 名称完全匹配的 baseline id 成功调用 `preset_validate`，才能接纳它。验证只是关联证据，不是语义展示证据。协调器轮询真实名单，并通过 `blueprint.get` 验证每个健康候选。其他候选只有在当前 Session 已记录的 mutation Tool 参数指向其 `agent.cordis.yml` 路径，或其 metadata 名称与 Draft 名称完全匹配时才会关联；无法归属或存在多个候选时保持 ambiguity。关联前，面板只显示 Draft。复制得到的 target 即使已通过挂载验证，只要其用户级语义节点仍与类型化 source 相同，就会继续显示空态；首个语义差异才会展示真实投影。通过验证接纳的既有同名 target 已经是真实内容，可以立即展示。开始展示后，每次成功投影都会处于当前 Creator 状态下，包括原生问卷和授权等待。节点始终可选并更新 Creator 对话上下文，但直接写入、Apply 与「试用 Agent」在 Ready 前保持禁用；后续 authoring 投影仍会保留有效 selection。Ready 要求没有运行中工作或待处理 interaction，并且出现晚于创建流程最近一次用户输入或原生等待点的结构化 `completed` turn；随后协调器会执行最后一次 `blueprint.get`，开放编辑与「试用 Agent」，为该 target 恢复提案上下文，且绝不切换 Creator Session。reconcile 会丢弃过期异步读取，并针对更新的 Session observation 重新执行，不会覆盖终止完成事件。

`试用 Agent` 会先等待当前 source Session 的 receipt hydration，再记录当前可见 Blueprint revision，并要求现有 Session API 使用该 preset 创建新 Session；hydration 期间切换 source Session 会取消这次 admission。成功的创建回执就是 Host composition commit：preset mount、Agent setup，以及 Tool、Skill、delegation、persona 和 permission assembly 均已完成，回执还会返回 live preset identity。Client 随后等待同一 Session 可被 client runtime 寻址，安装它的 Blueprint conversation context，完成后才打开会话；用户即使立刻发送也无法越过这些 readiness 步骤。P1 `blueprint.validateSession` 仍是 readiness 之后执行的更强 conformance 检查，而不用于定义 readiness。只有返回的 Session id、preset id 与 expected revision 都精确指向所创建 Trial 时，Client 才接纳验证结果。打开后的验证失败只会投影到该 created Trial Session；即使错误响应引用了第三个 Session，用户已经导航到第三个 Session 时也会抑制迟到结果。若准备期间用户已经切到别处，完成动作不会夺回导航。创建或打开该 Session 不会改变右侧 Blueprint target；对话上下文与 structured interaction 会继续使用该 target preset。Host 会验证 Session preset identity、实际 assembled Identity/Purpose/Behavior/Output 文本、完整 scoped Tool 名称与 model-visible schema digest，以及 resolved permissions。Try 的可选 P0 identity 来自当前 source Session 已恢复的 committed receipt 中，preset 与 committed revision 都精确匹配可见 Blueprint 且 durable Apply terminal 最新的一项；Proposal 顺序不能覆盖 Apply 顺序。刷新会保留这一关联，而 Session 切换与不匹配 receipt 会省略它。UI 只报告 runtime configuration 是否与 Blueprint 一致，不会声称 Try 应用或保存了某项更改。Prompt text、adapter address、anchor、digest 与 revision 均保留在内部。

打开后的 P1 校验失败只会显示在该 Trial Session 中；导航到第三个 Session 后，Client 会忽略迟到结果。Try 只会从当前 source Session 恢复的 committed Apply receipt 中发送可选 P0 identity，且其 preset 与 committed revision 必须与可见 Blueprint 完全匹配；刷新会保留该关联，Session 切换或 receipt 不匹配时会省略它。

Existing-Agent 对话可以通过 `route_blueprint_creator_authoring` 对明确创建独立新 Agent 的请求做类型化分类。Client 会让该 source Session 保持 foreground，在后台创建预留的 `cordis` executor，并在发送一条语言无关的 continuation message 前把类型化 route 记录到其中。Progress 与 terminal projection 只会返回确切的 source Session 与 route；打开 Creator timeline 从来不是 continuation requirement。刷新后会从 `blueprint/creator-authoring` 重建同一 lifecycle，包括 source Session、可选的开放 source-language metadata、Draft 名称与 route id。Existing-Agent 修改继续走 Proposal，Skill 与 Subagent 请求继续使用另一条绑定 target 的 capability-authoring route。现有 message parser 只作为直接发送到 `cordis` Session 的 legacy 创建请求的恢复 fallback。

后台 Creator 等待时，ui-blueprint 只会为当前 source route 选出确切的 child `PendingWait`，并通过 `ctx.conversation.interactions` 将它转发到该 source Session 的 composer。source 只拥有展示权：ui-blueprint 不复制也不回答 wait，原生 composer selector 会通过 child carrier 响应。切换 source Session、interaction 结算、route 消失或 plugin 释放都会清空先前 source 在该注册表中的列表。Host conversation-context DTO 只序列化持久 lifecycle、route、归属与 terminal 事实，绝不包含进程内 carrier；刷新后只有在 child Session 的正常 pending projection 可用时才会重新附加 carrier。参见[后台交互归属](../../../.agents/notes/implemented/bug-fix/2026-08-30-blueprint-background-interaction-ownership.md)。

没有任务级终态证据时，Creator 刷新恢复会读取 timeline 中最近一个具有持久 end 的 turn。末尾尚无 end 的 hydration turn 不能遮蔽之前已完成的 Creator turn，也不能让已验证 target 回退到 Paused。类型化 create-agent route 预留独立且确定性的 Creator Session id；Client 通过正常 Session 创建路径使用它，并将 continuation 交给 Host 的来源完全停稳校验与持久投递去重。恢复流程按确切的 source Session 与 route id 查找目标，并重试已接收但未投递的任务，不会启动重复执行。没有来源轮次凭据的历史 route 不能启动新的 continuation。

Skill authoring 观察 Host 解析的持久化结果，不要求先打开后台对话的聊天时间线。并发观察共享一次恢复和投影请求；确认终态后会刷新 target，并且只在所属 source Session 中持续显示。持久化失败保持可见，不伪装成成功完成。Subagent 完成仍保留独立的委派和 P1 检查。

类型化 Creator 任务在 Ready 后保留 route id。后续自由文本不能通过 legacy 解析器替换该身份。Host 恢复提供任务级终态证据；无关后续轮次不能重新激活其 Draft 或交互锁。只有不同的类型化任务身份才能开始另一生命周期。没有类型化任务的历史仍可使用纯文本恢复。参见[任务终态归属](../../../.agents/notes/implemented/bug-fix/2026-08-28-blueprint-creator-task-terminal.md)。

Proposal 卡片通过上下文同步从所属 Session 历史恢复 Apply 与 Cancel outcome。匹配的成功 receipt 在刷新及后续 preset 编辑后仍保持 Applied；匹配的 cancellation 会保持 Canceled，并且不会写 preset。两种 outcome 都会匹配完整的 source Session、route、Change Set、preset 与 base revision，并引用授权该 decision 的持久 Proposal 成功结果。Pending 卡片检查当前 revision、expected value 和可编辑性；当前文本相同不能证明历史 Apply。失败或拒绝的尝试保持独立状态，其他 Session 的 terminal 不能改变当前 target 或卡片。

Legacy untyped Creator recovery 只会分类最新的人类输入，因此后续 edit 或 capability turn 不会在刷新或 Session 切换后复活早已完成的创建请求。

## 模型体验

间接影响来自通过正常 runtime assembly 影响后续 Session 的 preset 修改；直接影响来自当前对话中带 scope 的所选 Agent Blueprint、可选 selected node、只生成预览的提案工具，以及绑定 target 的 capability-authoring 路由工具；它们只提供上下文，不会开启编辑模式。能力需求会排入一条包含目标结果的可见用户消息，并要求模型在当前 editable 结构足够时使用普通提案路径；用户不需要选择 Tool、Skill 或协作 Agent 术语。

#### KV Cache effect

选择 Blueprint 节点会改变当前对话中带 scope 的 runtime-context snapshot，直到 selection 改变或上下文被清除。Creator Ready 前，已关联 target 会把所选节点的当前真实值提供给 Creator authoring context，但不会安装提案 schema；明确调整会作为 Creator steering 处理，并等待真实 preset 重新投影。Ready 会把同一 selection 切换为 existing-Agent proposal context。成功写入可能改变此后新建 Session 的系统提示词前缀；运行中的 Session 保持其已经加入的 preset generation。

## 已知限制与暂缓事项

- **Selected context 只提供参考** —— 它会在普通 composer 旁和带 scope 的模型上下文中标识节点，但不会强制编辑。使用指代词的修改请求必须指向 selected node。
- **提案操作是闭集** —— editable Identity、Purpose、一个 editable Behavior、Web Search、Web Fetch 与 editable Output 是仅有的提案目标。File Read 只用于解释，不能产生 Apply 操作。
- **Creator 关联与完成相互独立** —— 新 preset 如果没有当前 Session 已记录的 authoring 路径，且 metadata 名称也不完全匹配，就会保持 ambiguity，即使它可能由当前任务创建。已关联且可挂载的 preset 在 Ready 前可见但只读；协调器不会解析 Assistant prose 或 reasoning 来强制匹配或宣告完成。
- **Capability mutation 仍是 Host 的闭集操作** —— 只有 Web Search 与 Web Fetch 具备类型化布尔写入。语义摘要不展示组件级开关；File Read 保持只读，Shell Background 不展示。
- **Skill 与协作 Agent mutation 仍归 Creator 所有** —— 已挂载的 scoped Skill 与已配置的 delegation capability 会以只读方式投影，client 目前没有通用安装、Skill authoring 或 delegation-row mutation API。类型化路由可以针对确切 existing target 启动 Creator authoring。专用 Subagent authoring 使用现有 `tool-subagent` composition 字段，并且只有后续真实挂载及 P1 重新投影成功才会被接受；UI 不会虚构搜索结果、协作者规格或 capability node。
- **非 loopback 不能 authoring** —— 在 Web transport 形成认证方案前，全部 Blueprint endpoint 都固定在 loopback。
- **Demo 状态不等于 Harness 执行** —— 内存 adapter 与 fixture timeline 只复现目标交互状态。Demo 验证可以描述其确定性本地结果，但不能显示 DSH runtime-conformance 成功文案。
- **Demo Mode 不拥有 UI** —— 它必须启动 production DSH Web shell 与 Blueprint slot component。另行设计一张仿制页面不属于该 package 支持的 Demo 路径。
- **Runtime conformance 不是 Eval** —— 「试用 Agent」只证明所选配置进入了新 live assembly；它不会评价回答质量、比较不同版本，也不会持久保存验证历史。
