# @deepseek-ai/dsh-client-ui-blueprint

English | [中文](README.zh.md)

The first usable Interactive Blueprint Agent Builder in the existing DSH Web shell. It fills four declared slots: the Agent roster in the sidebar, the Blueprint in the details column, selected context above the composer, and trial confirmation in the frame overlay.

The current Session and its Host-echoed `agentPreset` own the default Blueprint target. The browser preference stores an override together with that Session id, so an explicit Agent selection can change the right-hand target for one Session but cannot leak into another Session or the blank new-session screen. A Creator record or target-bound capability-authoring record may override the runtime preset only when it belongs to that same Session. On every current-Session transition the controller clears the previous projection before reading the new runtime identity, then reprojects from the precedence `same-Session authoring target → same-Session explicit selection → runtime agentPreset → deployment default`; missing or unreadable entries are discarded. Choosing Creator in the Agent roster stages `cordis` for the next Session instead of relabeling the current one. Before that Creator Session receives a creation request, its baseline `cordis` projection remains visible UI but is not installed as ordinary existing-Agent model context; this prevents the first Creator prompt from inheriting Proposal or new-Agent routing instructions. The details column groups projected nodes under Identity, Purpose, Capabilities, Behavior, and Output without translating their semantic values. Fixed labels use Chinese only for a `zh` source-language tag and otherwise fall back to English; this label fallback never changes the Agent's authored language. Direct edit buttons and capability switches otherwise follow `editable: true`. Purpose shows its complete committed text and reuses the inline text editor, including Cancel and Submit change, while a read-only legacy Identity exposes Adjust without claiming a safe Host write.

Creator recovery and asynchronous projection publish only for the current Session and its current foreground generation. Switching away does not delete authoring history or stop background execution; returning or refreshing restores that Session's own lifecycle. A source may show its own staged Draft before handoff, but cannot adopt the child's Creator state. Foreign or superseded results cannot change the target, context, or interaction lock. See the [foreground ownership decision](../../../.agents/notes/implemented/bug-fix/2026-08-28-blueprint-creator-foreground-ownership.md).

Every editable Identity, Purpose, Behavior, Output, Web Search, and Web Fetch control uses one structured interaction path. Submit creates a client route id and sends the source Session, selected node and type, committed expected value, and proposed scalar through conversation-context synchronization; it never calls a single-node write Remote or updates the Blueprint store. The Host validates the edit against a fresh committed projection, derives its operation and deterministic P2 candidates, records and flushes the route-owned input, wakes the source conversation, and returns matching enqueue evidence without writing the preset. The Client rejects missing or foreign evidence, and a failed editor remains open with its draft intact. The resulting Proposal card admits every supported structured node type, retains its source label in generic copy, and rejects Access. The committed Blueprint therefore changes only after the resulting Change Set is applied. Apply re-authorizes the exact operations from the source Session's durable Proposal Tool result, records a route-owned receipt, and performs one final reprojection. The UI never treats a draft, Proposal value, or model prose as committed Agent state. Selecting a node synchronizes optional context to the active conversation but never changes the preset.

The controller consumes a provider-neutral Agent catalog and Blueprint operation interface. The DSH Web binding maps the real preset roster and Host Remote into that interface. `InMemoryBlueprintDemoAdapter` implements the same roster, projection, narrow writes, capability toggles, atomic Apply, and reset behavior over caller-supplied seed data, so a static high-fidelity Demo can reuse the controller without embedding a final example roster or emulating the complete DSH API. It does not create Sessions, call a model, author Skills, or report runtime conformance.

Demo Mode is an alternate data binding, not an alternate page. `mountBlueprintDemoUi` registers the production roster, details panel, selected-context chip, proposal row, and trial overlay in their normal DSH slots. An opt-in Host composition may provide `demoBootstrapJson`; the Host half injects that parsed document before the shell runs, and the built Web shell activates the binding only when `?fixture&blueprintDemo` is also present. Layout, theme, navigation, conversation, and component CSS remain the real Web Client implementation. The optional `creatorScenario` stays outside the roster until a fixture Session using the real `cordis` preset receives an explicit create-Agent request. Fixture events then drive Creator progress and native approval, while Demo-local coordination publishes Purpose changes, a Skill node, a collaborator node, and trial verification. It calls no model, Tool implementation, Agent loop, Host write, or network endpoint. The verification state records only deterministic Demo flags and must not be presented as runtime conformance. The runnable `examples/web-blueprint-demo` overlay provides the repository preview entry.

`DemoScenarioController` owns the walkthrough lifecycle, Creator projection, Blueprint selection, proposal, capability-authoring, and trial state and projects only the compatibility fields consumed by the existing components. The connection fixture builds its transcript from production `SessionEvent` and pending-interaction frame fields through one timeline player. These replaceable fixture inputs support later product-to-prototype comparison; they do not define final interaction behavior.

Capabilities have one restrained `＋ 添加能力` entry and derive at most six repeatable work statements from real Purpose, Behavior, and Output nodes plus mounted runtime evidence. Agent-specific work such as application tracking, supplier due diligence, valuation comparison, or interview-theme clustering requires semantic source evidence. Enabled Web Search and File Read also receive concise user-level entries because omitting a real primary capability is misleading; those entries exist only when their actual Tool nodes are active. Scoped preset-local Skills and provider-backed delegations retain their own evidence, while inherited catalogs are not expanded into a component list. Every statement keeps its semantic and runtime supporting node ids internally; the UI shows only the concise work name in the Blueprint source language or the existing English label fallback. Selecting a statement supplies one supporting real node as conversation context.

The add entry asks what else the current Agent should do and starts a target-bound configuration state with a new `routeId`. The ordinary conversation receives the exact goal and must first decide whether the current editable Blueprint can implement it. That path keeps `propose_blueprint_change` available, but Identity, Purpose, and Behavior text cannot approximate an Add capability request. Only a typed `route_blueprint_capability_authoring` result carrying the same route and source Session may move the request into Creator authoring for a genuinely new Skill definition or Subagent configuration. The route preserves the current preset id and revision and never creates or copies a second top-level preset. When the source already runs `cordis`, that same Session owns authoring and repair after its routing turn ends; the client allocates no capability worker and the internal lifecycle transcript remains durable but absent from ordinary chat. A non-`cordis` source retains the deterministic dedicated-worker fallback, and legacy background records remain recoverable. The source Session and route own UI state and execution. While that lifecycle is active, edit, Apply, another Add, and Try are unavailable. The durable baseline retains the target revision, preset roster, projected nodes, Skills, and delegations; successful terminalization admits only the selected capability delta and rejects unrelated semantic changes or an extra preset. The controller retains the latest interaction for each source Session and derives the visible handoff only for the current foreground, while scanning only legacy distinct workers in the background. Pending observation matches the exact route instead of only the target and revision. Refresh recovery reconstructs the lifecycle's source, route, and terminal outcome without local completion storage; a new capability request from that source replaces the prior terminal. Canceling same-source authoring ends only that lifecycle and its exact inbox input; a legacy dedicated worker may still be stopped as a whole. A failed prompt continuation uses the same quiescence fence, so a lost response cannot publish a failure while authoring can still write. Skill and Subagent publication both require fresh target-bound runtime verification; a response that only describes a specification fails.

Explicit modification requests may produce a typed Change Proposal in the conversation. Its Change Set carries the source Session and interaction route. The Session-scoped row accepts metadata only when the Change Set id equals that exact Tool row's call id; for a structured edit, its first proposal must also match the source node id and type, the corresponding operation, the operation's scalar type, and a real current-to-proposed change. The row renders only for that owner; foreground navigation and another interaction against the same target cannot migrate the card. The card shows only the proposed effect and impact, and calls no write method until the user clicks Apply. Apply sends the exact owner and closed operation set to `blueprint.applyChangeSet`; the Host locates the source Session's successful Proposal Tool result, rebuilds its operations, and rejects a missing, foreign, or altered request before any preset write. Apply and Cancel share one per-preset serialized terminal decision. Repeating the same decision is idempotent, the opposite decision is rejected, and both outcomes are flushed to the source Session before returning. A successful transaction atomically publishes every preflighted operation or none, after which the client performs one final `blueprint.get`. Guarded recovery or concurrent-change results also refresh, while preflight and staging failures leave the displayed Blueprint unchanged. Discussion, judgment, and hypothetical messages produce no card.

In a `cordis` Creator Session, an explicit user request to create, build, or obtain a named Agent starts a Session-scoped Draft. A later clause that defers unrelated Skill or Subagent authoring does not negate that primary creation request; a locally negated create-Agent expression starts no Draft. The coordinator clears the previous Blueprint and editable conversation target immediately, then derives Creating, Waiting, and Paused from the existing running state, terminal turn reason, and native question or approval interaction. It can reconstruct that lifecycle after remount from the Session's durable user messages, settled Tool results, pending interaction, and latest turn end; the pre-creation roster is recovered by excluding presets attributed to later authoring evidence rather than treating the current roster as the baseline. Creating, Waiting, Paused, and Ambiguity install Creator authoring context and remove the Proposal Tool, so structured native-question answers continue authoring instead of being reinterpreted as an existing-Agent edit. A settled `preset_copy` contributes its typed source and target ids directly. Explicit native-question choices distinguish reuse of an existing preset, enhancement based on an existing preset, and creation of an independent preset. A reuse choice may immediately admit its named baseline preset; an undecided flow may admit an exact-name baseline only after this Session successfully calls `preset_validate` for that id. Validation is association evidence, not semantic reveal evidence. The coordinator polls the real roster and validates every healthy candidate through `blueprint.get`. Other candidates associate only when the current Session's recorded mutating Tool arguments name their `agent.cordis.yml` path or their metadata name exactly matches the Draft name; unattributed or multiple candidates remain ambiguous. Before association the panel shows only the Draft. A copied target remains in that empty state while its user-level semantic nodes equal the typed source, even after successful mount validation. The first semantic difference reveals the real projection; an existing exact-name target admitted through validation is already real content and can display immediately. After reveal, every successful projection is shown under the current Creator status, including native question and approval waits. Its nodes remain selectable and update Creator conversation context, while direct writes, Apply, and Try Agent stay disabled until Ready. Polling retains valid selection across later authoring projections. Ready requires no running work or pending interaction plus a structured `completed` turn newer than the latest creation-flow user input or native wait point, then performs one final `blueprint.get`, unlocks editing and Try Agent, restores proposal context for that target, and never switches the Creator Session. Reconciliation discards stale asynchronous reads and reruns against a newer Session observation rather than overwriting a terminal completion event.

`Try Agent` waits for the current source Session's receipt hydration, captures the visible Blueprint revision, and asks the existing Session API to create a new Session with that preset. A source Session switch during hydration cancels that admission. The successful create response is the Host composition commit: preset mount, Agent setup, Tool, Skill, delegation, persona, and permission assembly have completed and the response echoes the live preset identity. The client then waits for that same Session to become addressable, installs its Blueprint conversation context, and only then opens it; a user who sends immediately cannot enter before those readiness steps. P1 `blueprint.validateSession` remains the stronger conformance check that follows readiness rather than defining it. The response is accepted only when its Session id, preset id, and expected revision identify the created Trial exactly. A post-open validation failure is shown only in that created Trial Session; navigating to a third Session suppresses the late result even when the response cites that third Session. If the user navigates elsewhere while setup is pending, completion does not steal navigation. Creating or opening that Session does not change the visible Blueprint target; conversation context and structured interactions continue to use the target preset. The Host verifies the Session preset identities, assembled Identity, Purpose, Behavior, and Output text, complete scoped Tool names and model-visible schema digests, and resolved permissions. Try sends the optional P0 identity from the latest durable Apply terminal among the current source Session's restored committed receipts whose preset and committed revision exactly match the visible Blueprint. Proposal order cannot override that Apply order; refresh preserves the association, while Session switches and mismatched receipts omit it. The UI reports only whether the runtime configuration matches the Blueprint; it does not claim that Try applied or saved a change. Prompt text, adapter addresses, anchors, digests, and revisions remain internal.

An existing-Agent conversation may classify an explicit request for a distinct new Agent through `route_blueprint_creator_authoring`. The client keeps that source Session in the foreground, creates the reserved `cordis` executor in the background, and records the typed route there before sending one language-independent continuation message. Progress and terminal projection return only to the exact source Session and route; opening the Creator timeline is never a continuation requirement. Refresh reconstructs the same lifecycle from `blueprint/creator-authoring`, including the source Session, optional open source-language metadata, Draft name, and route id. Existing-Agent edits stay on Proposal, while Skill and Subagent requests retain the separate target-bound capability-authoring route. The existing message parser remains a recovery fallback for legacy creation requests sent directly inside a `cordis` Session.

When a background Creator waits, ui-blueprint selects the exact child `PendingWait` only for the current source route and forwards it through `ctx.conversation.interactions` into that source Session's composer. The source owns presentation only: ui-blueprint neither copies nor answers the wait, and the native composer selector responds through the child carrier. A source-Session switch, settlement, route loss, or plugin disposal clears the prior source's registry list. Host conversation-context DTOs serialize durable lifecycle, route, ownership, and terminal facts only, never the process-local carrier; refresh reattaches a carrier only after the child Session's normal pending projection is available. See [background interaction ownership](../../../.agents/notes/implemented/bug-fix/2026-08-30-blueprint-background-interaction-ownership.md).

Without task-level terminal evidence, Creator refresh recovery uses the latest timeline turn that has a durable end. A trailing hydrated turn without an end cannot conceal the preceding completed Creator turn or regress its validated target to Paused. Typed create-agent routes reserve a distinct deterministic Creator Session id; the Client uses it through normal Session creation and delegates continuation to the Host's source-quiescence check and durable delivery deduplication. Recovery searches for the exact source Session and route id and retries an adopted but undelivered task without starting duplicate execution. Historical routes without a source-turn fence cannot start a new continuation.

Skill authoring observes Host-resolved durable outcomes rather than requiring the background conversation's chat timeline to be open. Concurrent observations share one recovery and projection request; a confirmed terminal result refreshes the target and remains visible only in its source Session. Persistence failures remain visible and do not masquerade as successful completion. Subagent completion retains its separate delegation and P1 checks.

A typed Creator task retains its route id after Ready. Later free text cannot replace that identity through the legacy parser. Host recovery supplies task-level terminal evidence; unrelated later turns cannot revive its Draft or interaction lock. Only a different typed task identity starts another lifecycle. Text-only recovery remains available for histories without a typed task. See [task terminal ownership](../../../.agents/notes/implemented/bug-fix/2026-08-28-blueprint-creator-task-terminal.md).

Proposal cards recover Apply and Cancel outcomes from their Session history through context synchronization. Matching successful receipts remain Applied after refresh and later preset edits; a matching cancellation remains Canceled without writing the preset. Both outcomes match the complete source Session, route, Change Set, preset, and base revision, and cite the successful durable Proposal result that authorized the decision. Pending cards use current revision, expected value, and editability; current text equality never proves a historical Apply. Failed or rejected attempts remain distinct, and another Session's terminal cannot change the current target or its cards.

Legacy untyped Creator recovery classifies only the latest human input. A later edit or capability turn therefore cannot revive an older completed creation request after refresh or a Session switch.

## Model Experience

Indirectly, through preset changes that affect later Sessions; directly, while the active conversation receives the selected Agent's Blueprint, optional selected node, preview-only proposal Tool, and target-bound capability-authoring route Tool as scoped context rather than an edit mode. A capability request queues one visible user message containing the desired outcome and instructs the model to use the ordinary proposal path whenever the current editable structure is sufficient. The user never has to select Tool, Skill, or collaborator terminology.

#### KV Cache effect

Selecting a Blueprint node changes the active conversation's scoped runtime-context snapshot until selection changes or context is cleared. Before Creator Ready, an associated target supplies the selected node's current real value to Creator authoring context without installing the proposal schema; explicit adjustments remain Creator steering and wait for real preset reprojection. Ready switches the same selection to existing-Agent proposal context. A successful write can change the system-prompt prefix of Sessions created afterwards; a running Session keeps the preset generation it already joined.

## Known Limitations and Deferred Work

- **Selected context is advisory** — it identifies the node beside the ordinary composer and in the scoped model context, but does not force an edit. A deictic modification request must resolve to the selected node.
- **Proposals are a closed set** — an editable Identity, Purpose, one editable Behavior, Web Search, Web Fetch, and an editable Output are the only proposal targets. File Read remains explanatory and cannot produce an Apply action.
- **Creator association and completion are separate** — a new preset without a Session-recorded authoring path or exact metadata-name match remains ambiguous, even when it may have been created by the current task. An associated mountable preset is visible but read-only before Ready; the coordinator never parses Assistant prose or reasoning to force a match or declare completion.
- **Capability mutation remains a closed Host operation set** — only Web Search and Web Fetch have typed Boolean writes. The semantic summary does not expose component-level switches; File Read remains read-only, and Shell Background is not shown.
- **Skill and collaborator mutation remains Creator-owned** — scoped mounted Skills and configured delegation capabilities are projected read-only, and the client has no general install, Skill-authoring, or delegation-row mutation API. A typed route can start Creator authoring against the exact existing target. Dedicated Subagent work uses the existing `tool-subagent` composition fields and is accepted only after a later real mount and P1 reprojection; the UI does not invent search results, collaborator specifications, or capability nodes.
- **No non-loopback authoring** — every Blueprint endpoint is loopback-pinned until the Web transport has an authentication design.
- **Demo state is not Harness execution** — the in-memory adapter and fixture timeline reproduce only the intended interaction states. Demo verification may describe its deterministic local result but cannot render the DSH runtime-conformance success message.
- **Demo Mode does not own UI** — it must boot the production DSH Web shell and Blueprint slot components. A separately designed imitation page is outside this package's supported Demo path.
- **Runtime conformance is not an Eval** — Try Agent proves that the selected configuration entered the new live assembly; it does not score answer quality, compare variants, or persist validation history.
