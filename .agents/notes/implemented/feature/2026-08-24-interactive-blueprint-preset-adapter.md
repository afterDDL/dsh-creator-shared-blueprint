# Agent Note: Interactive Blueprint projects and narrowly edits agent presets

Status: implemented

English | [中文](2026-08-24-interactive-blueprint-preset-adapter.zh.md)

## Problem

An Interactive Blueprint cannot be validated from a parallel JSON model. The useful claim is a round trip over the composition the Harness actually mounts: read a preset and inherited policy, observe its scoped runtime assembly, edit a supported semantic field, write the preset, and prove a new Session receives the changed prompt sections, tools, and permissions. A generic YAML editor would make that loop easy to fake and would restore the arbitrary `!!js` write surface removed by [copy-only preset authoring](../simplification/2026-08-08-copy-only-preset-authoring.md).

## Decision

`@deepseek-ai/dsh-blueprint-adapter` is an opt-in Host service beside `ctx.agentPresets`. It projects preset composition text, `ctx.systemPrompt.assemble()` under the preset's standing scope or a live agent, the scoped `ctx.skills` snapshot, active literal `tool-subagent` rows, and `ctx.permissionPresets` into JSON nodes for Purpose, Identity, Capabilities, Behavior, Output, and Access. Every node states provenance, runtime status, editability, and an adapter-owned reference. Missing semantic sections remain missing. Skill nodes retain a Host-only definition digest and invocation policy; delegation nodes retain the configured row identity, provider, mode, persona summary, and current provider availability without treating a child Session as configuration.

Purpose and Output originate in the persona plugin's one prose scalar rather than separate configuration fields. [Explicit persona semantic anchors](../bug-fix/2026-08-27-blueprint-persona-semantic-anchors.md) retain their exact source paragraph and project a user-level value; safe legacy Purpose paragraphs remain inferred. Numbered Behavior items remain attributed to the preset. Capability nodes come from assembled tool schemas; Access comes from the Host default or the live session's pinned permission events. The root composition hash is the revision used by writes.

The write set is closed: a deterministic unique role span for Identity, Purpose, one numbered Behavior, a uniquely anchored numbered Output, and the explicit `tool-web.config.search` and `tool-web.config.fetch` booleans. Identity parsing retains the persona paragraph as source evidence, derives one semantic and display role without runtime-template prose, records the extraction kind, and separately records whether a narrow replacement exists. Creator-authored personas use a first-line `角色：…` or `Role: …` semantic source in the request language. Supported legacy introductions preserve their prefix, suffix, model variable, and working-directory variable during `updateIdentity`; deterministic legacy role clauses without one safe span remain selectable and read-only. A write resolves the preset through the roster, accepts only `user` trust, checks the revision and expected value, replaces one physical line or Boolean field, and atomically publishes the complete composition. It never reserializes the document. The [standing-generation mechanism](../architecture/2026-08-08-per-preset-standing-mounts.md) carries the edit to later sessions while existing sessions remain on their joined generation.

`tool-pwsh.config.enableRunInBackground` changes the live `pwsh` schema but the Blueprint does not project argument-level capabilities, so it is not an end-to-end mapping. `tool-fs` registers Read, Write, Edit, and optional image reading as one row with no per-tool enable field, so File Read is not independently writable. The adapter accepts an Output replacement only when the preset provides one unique numbered Output line. Exactly one standalone `输出：…` or `Output: …` persona line is projected read-only, and the adapter never creates a generic Output field.

The Web bundle mounts the adapter and its generated `blueprint` Remote namespace. `get`, `applyChangeSet`, `cancelChangeSet`, `setConversationContext`, and `validateSession` are loopback-pinned with the other privileged configuration calls; the five semantic operations remain internal to the atomic Change Set transaction. `@deepseek-ai/dsh-client-ui-blueprint` projects `competitive-research` into the existing sidebar, conversation input, details, and overlay slots. Its controls follow each node's `editable` flag, a committed transaction is followed by one fresh `get`, and Try Agent captures that projection revision before creating a new Session with the selected preset. The Client runtime's browser persistence retains only the last successfully projected preset id; startup accepts it only when the fresh roster and `blueprint.get` both succeed. Active capability authoring and active Creator association override that restored preference. A terminal lifecycle retains its valid target without restoring task state, but cannot replace a newer persisted or in-process user selection naming another target; an explicit selection made after startup also prevents later active automatic recovery from replacing it. Session creation and roster hydration do not own or replace the selected Blueprint target, so conversation context and structured interactions remain scoped to that target. Validation checks the durable and live joined preset identities, searches the live assembled section text for every projected Identity, Purpose, Behavior, and Output value, compares complete Tool presence and model-visible schema digests, compares scoped Skill identity, definition digest, and invocation policy, verifies delegation Tool and prompt evidence plus provider availability, and compares resolved permissions. It returns digest-only evidence and accepts optional P0 identity only from an exact durable Apply receipt recovered from the source Session; raw prompt, schema, and Skill-definition content remain on the Host.

The UI controller receives a provider-neutral roster and the closed Blueprint operation interface instead of the complete Client API. The DSH binding maps the real preset roster into that input and preserves its current preferred target policy. `InMemoryBlueprintDemoAdapter` accepts caller-supplied seeds and implements detached roster reads, projection reads, narrow writes, capability Tool-list updates, atomic Change Set preflight and commit, and reset entirely in browser memory. It has no built-in example Agent and exposes no runtime-validation method. A static Demo shell may simulate conversation and trial presentation, but it cannot present that simulation as a live DSH Session or reuse the runtime-conformance success state.

Demo Mode does not provide a second layout or component tree. `mountBlueprintDemoUi` registers the same production roster, details, selected-context, proposal, and overlay components into the normal Web Client slots, while the ordinary layout, theme, sidebar, conversation, workspace, and Session plugins remain mounted. An opt-in Host configuration accepts a JSON bootstrap document and injects it as `window.__DSH_BLUEPRINT_DEMO__` before the production shell starts; the browser still requires both `fixture` and `blueprintDemo` query flags before using it. The runnable `examples/web-blueprint-demo` overlay owns the temporary preview seed, a deferred Creator scenario, and a non-default port. Its focused fixture roster exposes only the shipped `cordis` entry and the demo-owned listed-company research Agent. New sessions begin with logged `danger-full-access` permission events, so the production picker presents Full access without changing ordinary fixture defaults. An explicit create-Agent request publishes the caller-owned scenario only after the Draft baseline is captured. Fixture Session events then drive Creator progress, native approval, and the trial transcript; Demo-local coordination publishes the Purpose change, Skill node, collaborator node, and local verification state. None of these steps invokes a model, Tool implementation, Agent loop, Host write, or network endpoint. The verification state proves only that the deterministic Demo flags were reached, not runtime conformance. Agent identity and scripted content remain caller-owned seeds rather than package defaults.

The static Demo entry mounts that same Web Client shell, slot registration, controller, bootstrap seed, and Blueprint-only fixture behavior without starting a DSH Host. Its in-memory connection implements only the Session, workspace, model, interaction, and projection reads and writes exercised by the accepted walkthrough; unsupported Remote calls fail instead of becoming a parallel backend. The build generates the Commands browser descriptor required by the existing Client UI, emits assets under a configurable repository base path, and excludes source maps. It does not open HTTP, WebSocket, provider, persistence, filesystem, Skill runtime, Subagent runtime, or Agent-loop connections.

`DemoScenarioController` is the only owner of the fixture walkthrough lifecycle, Creator projection, Blueprint selection, proposal, capability-authoring, and trial state. It projects a compatibility view into the existing production components. The connection fixture builds the scripted transcript from production `SessionEvent` and pending-interaction frame fields through one timeline player, so final-product captures can replace fixture inputs without replacing the UI tree. Neither the controller transitions nor the fixture timing defines final product interaction behavior.

The Capabilities section owns one `＋ 添加能力` entry instead of a separate plugin-management view. The client derives at most six repeatable work statements primarily from projected Purpose, Behavior, and Output semantics. Enabled Tools, scoped Skills, and configured delegation rows support those statements. Active Web Search and File Read also receive separate user-level summaries backed by their real capability node ids, while inherited Skill catalogs still do not create generic capabilities by themselves. Each statement retains semantic and runtime supporting node ids; raw names, ownership, providers, and modes remain available only in the Blueprint and P1 evidence. Selecting a statement installs one supporting real node as conversation context.

The add entry asks for the desired outcome and starts one target-bound configuration record. Ordinary existing-Agent conversation remains the default and keeps `propose_blueprint_change` available when the editable Blueprint can implement the request. A second preview-only Tool, `route_blueprint_capability_authoring`, may classify only an explicit request for a new Skill definition or Subagent configuration. Its typed result binds the current preset id and revision and performs no write. The [source-authority decision](../bug-fix/2026-08-30-blueprint-capability-authoring-authority.md) requires the Host to reconstruct every continuation field from that successful source Tool result and admits only the deterministic empty `cordis` child for its source Session and route. That Creator Session records the target preset, original request, typed authoring mechanism, exact baselines, explicit terminal outcome, and terminal sequence in `blueprint/capability-authoring` events. The Host reconstructs an unsettled context from those events after a client reload, while native pending interactions recover question and approval waits. During that recovery request, repeated Session snapshots cannot start the ordinary new-Agent observer; the observer runs only after recovery has classified the Session as ordinary Creator work. A terminal record suppresses reinterpretation of messages at or before its sequence, while a later direct user message may start independent work. A stale normal Blueprint context request cannot replace an active authoring binding. The record distinguishes assessment, proposal review, and Creator authoring, refreshes from real reprojection, and retains completion, failure, or cancellation for its source Session until another capability request replaces it. No speculative Blueprint node or installation result is created.

Subagent authoring uses a dedicated safe sequence because P0 cannot add an arbitrary composition row and change persona prose in one typed transaction. The durable start event captures the complete preset roster and target revision, every projected target node, every scoped Skill definition summary, and every delegation summary including a digest of its complete parsed config. The [exact-baseline decision](../bug-fix/2026-08-30-blueprint-capability-exact-baseline.md) permits only one new capability of the routed kind while every baseline capability, non-target preset, target metadata, and non-target semantic node remain exact. Creator receives an existing-target operation that forbids `preset_copy` and new top-level presets, permits only the real `tool-subagent` configuration fields, and requires a stable row and Tool identity plus an explicit collaborator name in `persona`. The [fixed Creator-only preset authoring Consumer](../bug-fix/2026-08-30-creator-only-preset-authoring-consumer.md) supplies `preset_validate`; that operation proves mountability but is not P1 authorization for semantic edits. The background Creator Session does not replace the user's current conversation. A completed Creator turn is not success by itself: the Host authoring resolver reprojects the target, requires exactly one new delegation with an enabled Tool and available provider, creates a dedicated verification Session, and requires matching P1 delegation evidence before checkpointing completion. The client publishes the verified projection and retains the source-owned terminal without requiring a loaded Creator timeline. Verification submits no model turn and does not spawn a business child; the temporary live Agent is disposed after its Session checkpoint. A missing row, unavailable provider, baseline change, failed conformance, rejection, cancellation, or stop closes the lifecycle without a formal capability. An active row with `maxDepth: 0` is a projection gap rather than a usable delegation because the first child call would exceed its depth limit.

Conversation context is Session-scoped rather than UI-only. `setConversationContext` registers one dynamic runtime-context contribution containing the current projection and optional selected node, plus `propose_blueprint_change` and `route_blueprint_capability_authoring`. Selection supplies context but never forces an edit. Both Tools create durable typed previews and perform no write. Proposal validation rejects non-explicit or hypothetical direct-user messages, stale revisions, incompatible operations, changed current values, read-only nodes, File Read, Shell Background, and unknown nodes; authoring-route validation rejects stale target or revision context and unsupported authoring kinds. The conversation card calls the existing semantic write only after Apply, then re-reads the Blueprint. Creator Draft and target-bound capability-authoring context remove both Tools. Scoped registrations are removed when context moves or the Session ends and are excluded from runtime validation because they describe the Builder conversation rather than the target preset.

Every editable Identity, Purpose, Behavior, Output, Web Search, and Web Fetch control follows the [structured-edit decision](../bug-fix/2026-08-30-blueprint-structured-purpose-edit.md). Its browser-local draft is inert before submission. Submission records a source-owned route and user-visible interaction without writing the preset; the first Proposal operation must reproduce that exact source edit, and later operations may target only Host-derived P2 candidates with explicit dependencies. The Tool row binds presentation to the exact call, source node, type, operation, scalar type, and changed value. Apply and Cancel reconstruct authority from durable source evidence and share one serialized terminal decision per preset. Apply preflights and stages the closed operation list against one composition, publishes the file once, flushes its exact receipt, and then reprojects. Cancel flushes its durable terminal without writing. Refresh therefore recovers the terminal decision, while the main Blueprint always projects committed state.

The client-side Creator coordinator recognizes an explicit request to create, build, or obtain a named Agent in a durable user message only while the Session runs the `cordis` preset. It replaces the unrelated Blueprint with a Draft immediately and derives Creating, Waiting, and Paused from the existing running state, terminal turn reason, and native question or approval interaction. The coordinator reconstructs that Session-scoped record after remount from durable user messages, settled Tool results, pending interaction, and the latest turn end. It recovers the pre-creation roster by excluding presets attributed to later authoring evidence from the current roster. Creating, Waiting, Paused, and Ambiguity remove `propose_blueprint_change`; native `ask_user_question` answers remain ordinary Creator authoring input. The Host rejects a stale invocation with `creator-authoring-in-progress` as defense in depth. A successful `preset_copy` contributes its typed source and target ids without prose or path inference. Explicit preset-strategy answers distinguish reuse, enhancement, and independent creation: reuse may admit the named baseline preset, independent creation excludes baseline presets, and enhancement waits for subsequent authoring evidence. An undecided flow may also admit one exact-name baseline after that same Session successfully calls `preset_validate` for its id; this typed evidence identifies a reused target but does not prove semantic customization. Roster polling admits only non-broken candidates whose normal `blueprint.get` projection succeeds. Other association remains Session-scoped: the candidate must appear in a mutating Tool argument as an `agent.cordis.yml` path recorded by that Session, or its normalized metadata name must exactly equal the Draft name. Before association the client shows only the Draft. One attributed candidate establishes the target, but a copied target remains in the Draft empty state while its user-level Blueprint nodes equal the typed source preset, including after mount validation; preset metadata and revision are excluded from this comparison. The first Purpose, Identity, Capability, Behavior, Output, or Access value difference makes the real projection visible, and visibility remains sticky for the lifecycle while later projections update it. A validated exact-name baseline has no copy source and displays its existing real projection once associated. Identity, Purpose, Capability, Behavior, and Output are then selectable; selection installs Creator authoring context containing the reprojected target and real selected-node semantics, not existing-Agent proposal context. Direct Host writes, Apply, and Try Agent remain disabled. Polling reprojects the associated target throughout authoring, retains any still-present selection, and refreshes its context after a revision change. Multiple or unattributed candidates remain ambiguous. Ready requires no running work or pending interaction and a structured `completed` turn newer than the latest creation-flow user input or native wait point, then reads the final Blueprint again before enabling edits and Try Agent and restoring proposal context. Reconcile work is coalesced by Session and discards a result when a newer observation changes the lifecycle record, so an earlier roster or projection read cannot overwrite the terminal completion state. Binding does not select a preset on the Creator Session, and Try Agent continues to create a separate Session.

An existing-Agent conversation exposes a dedicated `route_blueprint_creator_authoring` classification Tool beside, but separate from, Proposal and capability authoring. The Tool retains the exact direct-user request and emits a typed `create-agent` route; the client clears the old Blueprint, continues that route through the normal `cordis` executor, and records `blueprint/creator-authoring` in the target Creator Session before waking it. The event owns the source Session, route id, request, display name, and optional open `sourceLanguage` metadata. Lightweight Unicode-script detection records `zh`, `ja`, or `ko` when it recognizes that evidence; other text leaves the field absent, and Creator guidance preserves the original request's primary natural language without defaulting to English. Recovery also reads legacy events whose equivalent metadata remains under `language`. Remount recovery reinstalls Creator guidance from that event, so creation requests in any language share one typed executor path without keyword-dependent continuation. The existing parser remains only for legacy requests sent directly inside a `cordis` Session. Existing-Agent edits and target-bound Skill, composition, or Subagent authoring never use the new-Agent route.

The Proposal Tool likewise carries a typed `modify-existing-agent` or `reconcile-direct-edit` intent beside its closed operation list. The Host still binds the latest direct user message or direct-edit notice, current preset, revision, editable target, and expected value, but no longer needs a language-specific verb match after the model has selected the typed existing-Agent route. Requests in any language use the same Proposal executor without weakening the separation from Creator or capability authoring.

[Creator foreground ownership](../bug-fix/2026-08-28-blueprint-creator-foreground-ownership.md) excludes late or foreign publications across Session transitions. [Creator task terminals](../bug-fix/2026-08-28-blueprint-creator-task-terminal.md) prevent unrelated later turns from reviving completed authoring.

New-Agent execution transfer follows the [exclusive Creator handoff decision](../bug-fix/2026-08-28-blueprint-exclusive-creator-handoff.md); source termination and destination delivery do not change authoring or projection semantics.

[Routing provenance and arbitration](../bug-fix/2026-08-28-blueprint-routing-provenance.md) separates original Add capability input from guidance, constrains its target, and reserves one top-level operation per turn. Prose containing creation instructions is not active Creator state.

## Alternatives considered

**Rely on an unopened background conversation for Skill completion.** Rejected because a cold Session intentionally does not maintain the chat timeline consumed by the client observer. Host Session events and recovery instead resolve Skill terminalization through the serialized context operation. The durable start retains pre-authoring scoped Skill identities; success requires a new target-owned callable definition and fresh mounted Blueprint evidence after a completed Creator turn. The ended record is checkpointed before foreground cleanup, and duplicate observations reuse that outcome. Missing legacy baselines fail closed rather than being reconstructed from the post-authoring catalog. Subagent success retains its independent delegation/P1 checks.

**Infer Applied from current values or revisions.** Rejected because a later valid edit can replace the same value, and an unrelated write can reproduce a proposed value without ever applying that proposal. Conversation Apply records its terminal P0 result in `blueprint/apply-result` and awaits the Session persistence checkpoint. Recovery matches the Session, preset, Change Set id, base revision, and exact typed operations. A matching committed receipt takes precedence over current applicability; an unapplied proposal becomes stale only when its current revision or expected value no longer matches. Failed attempts never become Applied, and pre-existing histories without receipts are not backfilled from text. Preset commit and receipt persistence remain separate operations; a crash between them cannot be claimed as a receipt-proven Apply.

**Store a separate `blueprint.json` as authority.** Rejected because prompt sections, tool registrations, and permission inheritance would drift from a second editable model; generated JSON is an artifact, never the source of the session composition.

**Parse and dump the complete YAML document.** Rejected because a semantic edit would rewrite comments, ordering, block scalar style, and Loader-specific `!!js` expressions unrelated to the operation.

**Make every runtime tool editable by guessing its row.** Rejected because tool visibility does not identify one owning row or prove provider availability. The adapter admits only Web Search and Web Fetch, whose tool config already has explicit enablement semantics.

**Expose Tools, Skills, providers, and delegation rows as the capability UI.** Rejected because those objects explain implementation rather than what the Agent can do. They remain authoritative evidence, while the client derives a disposable semantic view with supporting node ids and never writes through that view.

**Make a static Demo emulate the complete DSH Client API.** Rejected because Session, transport, model, Creator, and conformance behavior would become a second fake runtime. The Demo implements only the provider-neutral state operations the shared Blueprint controller consumes; a later Demo shell owns explicitly labeled scripted conversation.

**Treat every Add Capability request as Creator authoring.** Rejected because many desired abilities are expressible by the current editable persona and mounted runtime. Entry-point provenance does not prove that a new Skill or Subagent is needed; only an explicit typed route may cross into existing-target Creator authoring.

**Restore arbitrary composition writes over the preset authoring API.** Rejected for the security and editor-quality reasons retained by the copy-only decision. A semantic Host operation is narrower in authority and failure modes than accepting composition text.

**Let the model call preset writes directly.** Rejected because ordinary discussion, hypotheticals, and stale conversational context would become mutation authority. The model may draft only a closed typed proposal; user Apply and the existing revision and expected-value checks remain mandatory.

**Automatically cascade a direct edit into related nodes.** Rejected because semantic consistency is a model judgment and the direct control authorizes only its own typed write. Causally related changes may share one visible Change Set, but the user must review and Apply it before any additional typed write begins.

**Parse the Creator's final Assistant message as completion.** Rejected because prose does not prove that a preset exists, mounts, belongs to this Session, or has stopped changing. Target association uses roster changes, normal Blueprint projection, and Session-recorded authoring evidence; completion uses the Session's structured running, pending-interaction, and terminal-turn state.

## Consequences

- Blueprint JSON is reproducible evidence over real composition and runtime services, not an editable shadow format.
- The same controller can run over the real DSH binding or caller-supplied in-memory Demo state. The latter proves UI state transitions only; it supplies no evidence about model execution, Session assembly, Skill authoring, or runtime conformance.
- Demo Mode replaces only the Blueprint data binding. It reuses the built production Web shell and slot components, while the opt-in Host overlay supplies preview data without changing production defaults, so a parallel hand-designed page cannot drift into becoming the public demonstration.
- Purpose and Behavior writes currently require unique single physical lines. Other persona styles remain readable when classifiable and otherwise produce no invented node.
- Web Search and Web Fetch are the only capabilities admitted by `setCapability`. Shell Background needs an argument-level Blueprint node before admission, and File Read needs a plugin-owned independent enable field rather than row surgery.
- Scoped mounted Skills and active literal delegation rows remain read-only evidence but are not listed individually. The semantic view exposes up to six concrete repeatable-work statements derived from Purpose, Behavior, and Output, retains semantic and runtime supporting node ids internally, and may omit shared or unclassified catalog entries without changing the Blueprint or P1 catalog. Existing-structure requests keep the Proposal, P2, P0, and P1 path; only a typed target-bound route enters Creator authoring for a new Skill or Subagent. The client exposes no marketplace, install result, pending capability authority, Skill mutation, or subagent authoring API; later real projection remains the only success signal.
- An MVP Output write can target an existing uniquely numbered Output item with revision and expected-value checks. It must not create an Output item or claim portability across arbitrary persona prose.
- Enabled Web Fetch may still lack an executable provider because the Web service intentionally exposes no provider inventory and tools remain schema-visible through provider outages; the Blueprint records this as a mapping gap.
- Permissions are stable read-only Access nodes. Changing them through a preset would violate their Host/settings/session ownership.
- A selected node changes the active Session's model-visible prompt context but does not authorize mutation. Proposal generation is conservative: ambiguous discussion produces no proposal, while Apply remains the authoritative freshness check.
- Every editable structured control retains a browser-local draft until submission, then creates one route-owned Change Set whose exact source edit comes first and whose P2 additions are deterministically bounded. No preset write occurs before Apply; Apply or Cancel is durable and source-owned, and the Blueprint continues to display only committed state.
- The copy-only authoring Note stays active: browser preset authoring still accepts no YAML, path, or composition text. The semantic Remote API does not weaken that wire rule.
- Creator coordination separates target association, semantic visibility, selection, direct writes, and authoring completion. A copied target does not expose source-template content until one user-level node differs; after that point the associated target remains visible and selectable throughout non-Ready states, which route explicit adjustments through Creator steering and expose no Proposal Tool or concurrent Host write. Ready enables direct editing and Try Agent and restores existing-Agent proposal context only after the final fresh projection. The coordinator does not translate reasoning, duplicate native questions, switch the current Session, or force a semantic-similarity match; versioning, parameter-level capability editing, permission editing, and diff views remain outside this decision.
- The standing-mount Note stays active: its generation and live-session guarantees are the mechanism that makes write-back observable without changing Preset or Session core logic.
- Runtime conformance proves that the current expected Blueprint revision is still current and that the new Session's live prompt content, Tool schemas, and permissions are equivalent. The preset service does not expose a generation's source revision hash, so the result explicitly reports that strict revision binding is unavailable. This check is configuration evidence, not an answer-quality Eval, A/B test, score, or persisted history.
